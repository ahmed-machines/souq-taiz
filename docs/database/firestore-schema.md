# Firestore schema

All timestamps are server timestamps (`request.time` is enforced in rules on create). Documents never contain unbounded arrays: image lists are capped at 8, search keywords at 10, conversation participants at 2. Messages, favorites and notifications live in subcollections.

## Collections

| Collection | Doc id | Owner / writer | Notes |
|---|---|---|---|
| `users/{uid}` | auth uid | client creates once as `buyer/active`; may edit `displayName`, `phone`. `role`, `status` are written only by Cloud Functions | private (email, phone, role, status) |
| `user_profiles/{uid}` | auth uid | owner | public: `displayName`, `photoUrl` |
| `users/{uid}/favorites/{listingId}` | listing id | owner | doc id = listing id, so duplicates are impossible |
| `users/{uid}/notifications/{id}` | auto / `msg_{conversationId}` | Cloud Functions create; owner can set `read` | types: `listing_approved`, `listing_rejected`, `new_message`, `account_status` |
| `categories/{id}` | slug | admins | `nameAr`, `nameEn`, `order`, `parentId` (subcategory), `iconKey`, `isActive` (soft delete) |
| `locations/{id}` | slug | admins | `nameAr`, `nameEn`, `parentId` (governorate → area), `isActive`. No neighborhood list is hardcoded |
| `listings/{id}` | auto | owner (limited) / Cloud Functions (moderation) | see below |
| `conversations/{listingId_buyerId}` | deterministic | the two participants | `participantIds[2]`, `participantNames`, `listingId`, `lastMessage*` |
| `conversations/{id}/messages/{id}` | auto | participants | `senderId`, `text` (≤1000), `createdAt`, `readAt` |
| `reviews/{sellerId_reviewerId}` | deterministic | reviewer creates `pending`; admins moderate | one review per pair; no self-review |
| `reports/{listingId_reporterId}` | deterministic | reporter creates; Cloud Functions resolve | one report per user per listing |
| `admin_logs/{id}` | auto | Cloud Functions only | immutable audit log |
| `app_settings/{id}` | key | super admin | public read |

## Listing document

```
ownerId, ownerName (denormalized), title, description,
categoryId, subcategoryId?, locationId,
price (number), currency ('YER'), priceType ('fixed'|'negotiable'),
imageUrls[1..8] (first = cover), coverImageUrl, contactPhone,
searchKeywords[≤10] (normalized title tokens),
status, isFeatured, rejectionReason?, viewCount,
createdAt, updatedAt
```

Server-owned (clients cannot set or change them): `isFeatured`, `viewCount` (always 0 – view tracking is **not implemented**, so the UI does not show views), `rejectionReason`, and any move to `published`/`rejected`.

### Status lifecycle

```
draft ─┐
pending_review ──(admin approve)──► published ──► paused ──► pending_review
rejected ─(edit)─► pending_review     │               └──► archived
                                      ├──► sold ──► archived
                                      └──► archived
```

Owners may only perform the transitions enforced in `validStatusChange()` in `firebase/firestore.rules`. Editing content forces `pending_review`/`draft`. **Deletion is soft**: owners archive; hard deletes are denied by rules.

## Query patterns & pagination

* Search (`FirestoreSearchService`): `status == published` + optional equality filters (`categoryId`, `subcategoryId`, `locationId`, `isFeatured`) + optional `searchKeywords array-contains <first token>`, ordered by `createdAt` (asc/desc) or `price` (asc/desc; price range applied server-side). Cursor = last `DocumentSnapshot` (`startAfterDocument`), page size 20. For date sorts the price range and extra keyword tokens are refined client-side with up to 5 refill fetches.
* Owner listings: `ownerId [+ status]` ordered by `createdAt desc`; counts use `count()` aggregations.
* Conversations: `participantIds array-contains uid` ordered by `lastMessageAt desc`, limit 30. Messages: newest 50, live listener disposed with the page.
* Related listings: published + same category, newest first.

Indexes are generated by `node tool/gen_indexes.js` into `firebase/firestore.indexes.json` (see [indexes.md](indexes.md)).

## Retention

No automatic deletion is configured. Archived listings and resolved reports are retained for audit. Recommended (not implemented): a scheduled function to purge archived listings and their images after a retention period.

## Known limitations

* Keyword search is token-exact (no prefix/fuzzy/typo tolerance). `ListingSearchService` is the seam for Algolia/Typesense/Meilisearch.
* `ownerName` is denormalized and is not updated when a user renames themselves.
